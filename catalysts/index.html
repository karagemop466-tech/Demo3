Swing & catalyst ledger

Every market move of ≥ $0.10 per contract in either direction, in the five tracked topics, with the website links that may have caused it — a headline published inside the swing window that shares keywords with the market. Links are candidates, never claims of cause: Kalshi's API exposes no news field, so the matching rule is published in full. Each row links the exact official API record it came from; anything the API did not return is blank and flagged, never filled in.

How a link becomes a "candidate catalyst"

  
    
    
  1. Swing rule. Consecutive samples of the same market, in exact decimal
    dollars: |last − previous| ≥ 0.10 either direction. Float arithmetic is
    never used, so nine-cent moves cannot round up into an alert.
    2. 
    
  2. Window. A news item qualifies only if its published timestamp falls inside
    [swing start − pre, swing end + post] (currently shown in the run status;
    default 180 min before, 60 min after).
    3. 
    
  3. Relevance. The item title must share at least two significant words with the
    market/series title, or one word of six+ letters. The matched words are printed with every link so
    you can judge the hit yourself.
    4. 
    
  4. Provenance. Each feed item stores its own URL plus the feed URL that produced
    it; each market row stores the exact API request its numbers came from. Official series
    settlement_sources — the sources Kalshi itself cites for that series —
    are listed separately, because they come back from the API rather than from a guess.
    5. 
    
  5. Fail closed. No qualifying item ⇒ empty cell + reason
    (items_in_window_but_no_keyword_overlap or
    no_feed_item_in_window). No feed parsed ⇒
    no_feed_items_available. Nothing is back-filled from memory.
    6. 
  






  
Flagged for review (this page)

  
Also recorded in COORDINATION.md for the
  integration session to mirror into the site-wide
  Flagged for review page.

  
    
    
  • F-cat-01 · detection depends on the sampling gap (high). A swing is only
      visible if two samples straddle it, so a move that reverts between samples is missed. The
      scheduled run and the in-browser watch set that gap; Kalshi's WebSocket feed would close it
      entirely, but its handshake requires KALSHI-ACCESS-* headers a
      browser cannot attach, so this layer stays on REST polling.
      WebSockets docs
    • 
    
  • F-cat-02 · catalyst links are correlation, never cause (high). No Kalshi
      field ties news to a price. The rule published above decides every link, and the demo
      exchange is explicitly a testing environment whose prices may not track real markets.
      Demo environment docs
    • 
    
  • F-cat-03 · the feed allowlist is unverified from this build environment (medium).
      The sandbox that assembled this page can reach only github.com / npmjs.org / pypi.org, so no
      RSS host could be checked here; every entry in catalysts/feeds.json
      is labelled pending_ci_probe and only the scheduled probe can make it
      usable. Prune anything that keeps failing. (No feed has been dropped either — the health table
      shows the real result.)
    • 
    
  • F-cat-04 · the demo ledger is thin and partly synthetic (medium). The
      collector's own notes record synthetic exchange-test series (for example the hourly
      KXDEMOFUTHOURLY demo-BTC markets) ranking high on demo volume; the
      seeded swings on this page come from exactly such a market. Treat the ledger as a mechanism
      proof until the owner decides which series count as real
      (Questions).
    • 
    
  • F-cat-05 · GET /events?event_tickers=… ignores its filter on
      this deployment (verified here, 2026-11-20). The request for one hourly event returned
      unrelated events, so this layer looks markets up by /markets?tickers=
      and /markets/{ticker} only. The endpoint table above re-checks it on
      every run.
      Get Events docs
    • 
    
  • F-cat-06 · limit is not honoured on
      GET /series?category= (verified here, 2026-11-20). A request
      with limit=3 returned the full category page set, so catalog paging here
      is cursor-based — this corroborates F9 recorded by session 6908a11a.
      Get Series List docs
    • 
    
  • F-cat-08 · the exchange cross-check covers prices, not the interval. The
    official market record publishes previous_price_dollars and
    last_price_dollars, which lets the exchange corroborate a row's two
    prices (the 2026-11-20 KXPRESNOMD-28-BOBA row is labelled
    exchange-corroborated for exactly that reason: its tape prices
    0.0050 → 0.8630 reproduce the record's own
    previous → last). It publishes no timestamp for
    previous_price_dollars, so the time the move took remains bounded only
    by the sample gap, and rows whose record lacks those fields are labelled
    not cross-checked rather than assumed correct.
    • 
    
  • F-cat-09 · no per-event page URL is published. The demo desk host is documented
    (demo environment →
    demo.kalshi.co) but the URL pattern for a single event is not,
    and this build environment cannot load the site's app to confirm one. Guessing
    /market/<event> would be an inferred value, so each row links the
    canonical API records (market / event / series) plus the host root instead, and
    kalshi_market_page is published empty with the reason in
    kalshi_market_page_note.
    • 
    
  • F-cat-10 · a "jump" can be one print against a wide quote. The
    KXPRESNOMD-28-BOBA sample that produced a $0.858 move reported
    yes_bid_dollars 0.0010 against yes_ask_dollars
    0.8630 and price_level_structure "deci_cent" (1/10-cent ticks, so
    858 ticks in one sample); lifetime volume is 418,777,737 contracts while
    volume_24h_fp is only 63,615. Every row therefore
    prints the quote and the ladder next to the move: a large Δ in a thin book is not a tradable signal,
    and this page makes no claim that it is.
    • 
    
  • F-cat-07 · this page is not in the site navigation yet (process). Root nav
      and the root Flagged page are shared outputs owned by the integration session; change requests
      CR-22661044-1/2 are logged in COORDINATION.md instead of editing them.
    • 
  


  
Suggestions for making this layer more live and interactive

  
    
    
  1. S-cat-01 — signed WebSocket relay (a small worker holding the
      ticker/trade channel and republishing to
      browsers) removes both the polling gap and F-cat-01.
    2. 
    
  2. S-cat-02 — alert on orderbook shape, not just last price: bid/ask collapse or
      a one-sided ladder of ≥ N contracts at a level is an earlier, cleaner signal than a trade.
    3. 
    
  3. S-cat-03 — per-topic daily digest ("what moved and what was published around
      it") generated by the same scan, so the ledger is readable without a live tab.
    4. 
    
  4. S-cat-04 — a pre-trade checklist beside each alert: spread, top-of-book size,
      time to close, and the estimated-dollar caveat, so a trader can act without leaving the page.
    5. 
    
  5. S-cat-05 — a thumbs up/down on every alert fed back into
      catalysts/data/feedback.json; that labelled history is what a real
      high-ROI screen needs (today's filter on the dashboard is an explicitly labeled placeholder).
    6. 
    
  6. S-cat-06 — candlestick overlay with the spread shaded, plus click-and-drag
      zoom on the time axis.
    7.
