## Q-03

### Which dollar definition should the leaderboard rank on?

**Why it matters.** There is no dollar-volume field, so any ranking is a modelling choice; the choice changes the order of every row.

**Known (verified).**

- GET /markets and GET /series publish volume_fp / volume_24h_fp in CONTRACTS, and notional_value_dollars per contract (1.0000 on every market sampled).
- The tape (GET /markets/trades) gives count_fp plus yes_price_dollars and no_price_dollars per fill, so dollars must be summed from fills.
- Both parties in a trade pay the same price, so pricing the taker's own side is the least assumptive choice.
- Current formula: sum over trades of count_fp x (yes_price_dollars if taker_outcome_side=='yes' else no_price_dollars).

**Missing.** Whether you prefer (a) taker-side notional, (b) YES-leg notional only, or (c) contracts.

**How to find out.** Compare the two formulas on the same capture: scripts/aggregate_capture.py prints taker-side; scripts/analyze.py prints YES-leg notional. Both numbers are on the site.

**Suggestion.** Keep taker-side notional as the ranking key (it matches what money actually moved), and always show contracts next to it so a $1-notional assumption is visible.

**Sources.**
- <https://docs.kalshi.com/api-reference/market/get-trades.md>
- <https://docs.kalshi.com/api-reference/market/get-series-list.md>
- <https://docs.kalshi.com/api-reference/market/get-markets.md>

## Q-09

### What polling budget is acceptable for unauthenticated public reads?

**Why it matters.** Unauthenticated limits are documented as separate and stricter, with no published numbers; over-polling is the fastest way to 429 the dashboard.

**Known (verified).**

- Rate limits use a token bucket: default 10 tokens per request class, separate Read and Write budgets, a 3-second burst window at Basic/Advanced read levels, and no Retry-After header on 429.
- Public unauthenticated traffic has its own undocumented limits.
- The docs state REST responses are cached briefly, so sub-second polling returns stale data anyway.
- GET /series ignores a limit parameter and has no cursor, so a full sweep is one large response, not a paged loop.

**Missing.** A budget you are comfortable with for continuous collection (interval and pages per run).

**How to find out.** Watch X-RateLimit-* headers on responses during a test run; that is the only empirical way.

**Suggestion.** Default the UI to 15 s with 8 tape pages, keep any cron at 1-5 minutes, and back off on 429 without retrying immediately.

**Sources.**
- <https://docs.kalshi.com/getting_started/rate_limits.md>
- <https://docs.kalshi.com/api-reference/market/get-series-list.md>

## Q-12

### Should the order book ladder keep showing only bids plus an implied ask, or persist derived asks as their own field?

**Why it matters.** The ask side is a derivation, not a read; presenting it as data would be a fabricated value.

**Known (verified).**

- orderbook_fp returns yes_dollars and no_dollars as [price_dollars, count_fp] arrays, ascending, bids only, best last.
- A YES bid at X is equivalent to a NO ask at 1 - X, which is how the ladder prints the ask side.
- depth=N controls how many levels come back; the ladder uses the raw bids and shows the derivation inline.

**Missing.** Whether you want the derived ask stored in data/ at all, or shown only in the UI.

**How to find out.** No research needed; both options are one-line differences in collect.py.

**Suggestion.** Show it in the UI labelled 'implied', never write it into the published data as if it were an API field.

**Sources.**
- <https://docs.kalshi.com/getting_started/orderbook_responses.md>
