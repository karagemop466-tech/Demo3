## 2. Irregularities found (flagged for review)

### R-91-01 — Live order entry in `assets/trade.js` does not match the V2 order schema — **high**

`assets/trade.js` (main, lines 87–100) posts to `/portfolio/events/orders` with
`action: "buy" | "sell"`, `side: "yes" | "no"`, `count: <number>`, `yes_price: <cents integer>` and
`price: <dollars float>`.

The official V2 request body is:

```json
{ "ticker": "...", "side": "bid" | "ask", "count": "10.00", "price": "0.5600",
  "time_in_force": "good_till_canceled", "self_trade_prevention_type": "taker_at_cross",
  "post_only": false, "client_order_id": "..." }
```

i.e. **`side` is `bid`/`ask` (not yes/no)**, counts and prices are **fixed-point strings**, the price
field is `price` (there is no `yes_price` in V2), and `time_in_force` values are
`good_till_canceled` / `immediate_or_cancel` / `fill_or_kill` rather than the `gtc`/`ioc`/`fok`
shorthands the page sends.

* Source: [Create Order (V2)](https://docs.kalshi.com/api-reference/orders/create-order-v2)
* Impact: **live** order submission from the root dashboard would be rejected (400) as written. It
  is inactive today because no demo credentials exist in the repo (flag L-07 / I-12), so no bad
  order has ever been sent — but the path must be fixed before credentials are added.
* Paper mode is unaffected (it never calls the API).
* Status: **needs review** — the file is outside this session's scope (`live/`); the fix is a
  one-function change in `assets/trade.js`.

### R-91-02 — Live-order branch in `scripts/kalshi_client.py` always signs RSA-PSS — **medium**

`scripts/kalshi_client.py` loads any PEM but signs with
`padding.PSS(MGF1(SHA256), salt=DIGEST_LENGTH)` unconditionally. That is correct for RSA keys, but
the docs now generate **Ed25519 keys by default** ("Ed25519 is selected by default"), and Ed25519
keys must sign the message directly. `collector/kalshi_api.py` and `trading/kalshi_trade.py` already
handle both; only this older helper does not.

* Source: [API keys](https://docs.kalshi.com/getting_started/api_keys) (key-type table)
* Impact: with a default (Ed25519) demo key, requests signed by `scripts/kalshi_client.py` fail
  signature verification. Not used by `live/` (read-only), so no exposure there.
* Status: **needs review**

### R-91-03 — `assets/alerts.js` high-ROI filter is a placeholder rule — **medium (disclosed)**

`assets/alerts.js` (main) flags an alert high-ROI when the swing is ≥ $0.10 **and** at least 10% of
price. The file itself says it is "a transparent placeholder heuristic. No model is defined in this
repo". That disclosure is accurate and is repeated on the page, so it is not a false claim — but it
is not an ROI model, and the two chat streams on the root dashboard therefore show a duplicated
signal rather than an independent filter.

* This session's `live/` module replaces it with a published EV model
  (`p_hat = mid + 0.5·momentum − 0.15·spread`, high-ROI at EV ≥ $0.03 and ROI ≥ 10%) and measures the
  model's own simulated track record, so the filter can be judged by results.
* Status: **needs review** (root file outside this session's scope)

### R-91-04 — Alerts built only from in-browser polling — **medium**

The root dashboard's swing detection samples the last traded price only while the page is open, so
history is lost on reload and nothing alerts when the tab is closed. The `live/` desk detects swings
from committed candlesticks (so alerts survive reloads and exist without a viewer) and adds optional
live polling on top. Suggest server-side alerting (already item 24 on the Suggestions page).

* Status: **needs review**
